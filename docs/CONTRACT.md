# Desktop bridge contract

The desktop frontend calls `invoke('dispatch', { request: { action, payload } })`. All JSON fields use camelCase. Responses are direct values, errors are sanitized human-readable strings. Errors in operations that span several accounts, domains, links or platform addresses name the affected item by its local label, host, slug or platform name (never a secret). A non-2xx Cloudflare API response keeps `HTTP nnn` in the message; only 400/401/403/404 point at the token; a rate limit (429), service error (5xx) or any other 4xx never mentions tokens, permissions or error codes, and other 4xx may add `Cloudflare 代码 N` read from a size-limited body. A failed write whose outcome is uncertain (5xx, 408, or a transport error after the request may have been sent) says so and points to the pending operations instead of suggesting a plain retry; this holds for generic writes, KV value writes and Worker uploads alike. A write whose connection never opened (connect or TLS failure, so nothing was sent) is a definite failure, not uncertain: `连不上云端，这一步没有发出去，请检查网络后重试`. The text covers only that request; when earlier steps of the same operation were already applied, the caller still reports its rollback result. The frontend cannot supply API URLs, resource IDs for deletion, or arbitrary HTTP requests. Backend plans are authoritative, single-use and expire after five minutes (the only exception is a domain plan whose review failed on the network alone; see `apply_plan`). Every remote write requires a prepared plan and explicit confirmation.

## State

`get_state` → `{ appVersion: string, accounts: Account[], domains: Domain[], links: Link[], pendingOperations: string[] }`

- Account: `{ id, label, cloudflareName?: string, zones: {id,name,status}[], zoneCount, checkedAt, hasResources, needsSelftestKey, needsCredentialMigration: boolean, needsTokenRecovery: boolean }`. `cloudflareName` is the provider account name, not a login email; `label` remains a local remark. Names and zones are refreshable cache, not new backup authority. `needsCredentialMigration` is derived from local macOS credential metadata without reading secrets; it is always false on Windows. `needsTokenRecovery` reflects a locally persisted, incomplete token import; it does not prove that the credential is absent. Credential-dependent reads and cloud mutations remain blocked until explicit token recovery succeeds. Local viewing, renaming and removal remain available. The frontend types permit these flags to be absent for compatibility; absence is treated as false. Neither flag is accepted as backup authority.
- Domain: `{ id, accountId, zoneId, host, prefix, routeId }`
- Link: `{ domainId, slug, cnUrl, defaultUrl, updated }`
- Plan: `{ id, title, steps: string[], warnings: string[], expiresAt }`
- Check: `{ label, ok, message }`
- DomainCheck: `{ label, ok, message, level: 'pass' | 'warning' | 'error', reason?: string }`; used only by domain preparation. A warning is not proof that a path is empty or that routing is already working. `reason` is a stable machine-readable cause; the frontend must use it instead of matching message text. Besides the local-check reasons (`dns_timeout`, `dns_failed`, `public_dns_timeout`, `public_dns_failed`, `virtual_dns_address`, `blocked_non_public_address`, …) it may be:
  - `cloud_unreachable`: a Cloudflare API read (zone, DNS records or Worker routes) got no HTTP response (connect failure, timeout or aborted request) after its automatic retries. A Cloudflare error response (for example HTTP 403) is not this reason; it keeps its own message, and only a 401 or 403 carries a reason (`cloud_refused`).
  - `cloud_refused`: a Cloudflare API read for this check (zone, DNS records, Worker routes or the prefix config read of the `转发规则` check) was answered with HTTP 401 or 403. This is a real answer, not a network failure. When a 403 on the zone read leads to the one-off zone refresh and the original check is kept, it keeps this reason.
  - `credential`: the check failed because this computer could not use the account's saved authorization (the checks labelled `本机授权` and `凭据`, in `prepare_domain` and `prepare_domain_dns`).
  - Checks built from the website probe (`短链接目录`, `随机测试链接`) and the `域名归属` "not found in this account" check never carry `cloud_refused` or `credential`.
  - `probe_timeout`: the anonymous directory probe timed out.
  - `probe_transport_error`: the directory probe could not connect (including TLS) or its request was interrupted.
  - Transient network reasons are exactly `dns_timeout`, `dns_failed`, `public_dns_timeout`, `public_dns_failed`, `cloud_unreachable`, `probe_timeout` and `probe_transport_error`. Repeating the same check is safe. All other reasons (for example `virtual_dns_address`, `invalid_url`, `public_dns_invalid_response`, `public_dns_response_too_large`, `dns_no_answer`) are definitive for the selected DNS mode.
- Plan may include `domainTakeoverConfirmation: string`. This server-generated text describes the exact hostname and directory whose existing responses will be replaced by the short-link service.
- Plan may include `credentialMigrationConfirmation: string` for an explicit local macOS credential migration. Its confirmation is independent of domain takeover consent.

## Actions

- `token_template` `{}` → URL string. A frontend opener opens exactly this URL in the system browser.
- `import_token` `{ token, replace: boolean, expectedAccountId?: string }` → State plus a one-off `importReport: { imported: {id,name}[], skipped: {id,label}[], rejected: {id,name,reason}[] }` that is never persisted. A token may list several accounts. Without `expectedAccountId` the import only adds accounts that are not completed locally: a completed account is skipped, is not probed with the pasted token, and keeps its saved credential and cached data whatever `replace` says. An account for which Cloudflare refuses the required reads is left out and listed in `rejected` without blocking the others; a network, rate-limit or service failure aborts the whole import and is not reported as a missing permission; when the token lists several accounts that error starts with `读取账户「{Cloudflare name}」时出错：` and says that no account was imported. When nothing can be imported the call fails, names the accounts and reasons, and changes neither state nor credentials. Replacing a saved credential is only possible through the scoped update: supplying `expectedAccountId` requires a matching existing local account and `replace:true`; the active token must list that account, and only that account is updated, preserving its local label. Validate every account that will be written before changing local state or credentials. Persist visible account placeholders with `needsTokenRecovery:true` before any secret write; failure to persist this intent prevents secret writes. New or unresolved credential entries use create-only/read-back checks: retrying the same token is allowed, but a different token for a pending account requires both the explicit target and replacement confirmation. A broad `replace:true` without `expectedAccountId` does not authorize overwriting a pending account's different credential. Clear the pending markers only after all selected secret writes and final state persistence succeed. A write, read-back, interruption or final persistence failure leaves the visible pending state for an explicit retry; do not silently overwrite unknown credentials, delete saved credentials as compensation, resume cloud work or claim import success. No token or token-derived digest is stored in local configuration or returned through State. Updating a token does not clear an independent credential-migration requirement.
- `rename_account` `{ accountId, label }` → State.
- `remove_account` `{ accountId }` → State. Local removal only; remove local associated records and current credentials, preserve remote resources and retained legacy macOS credential entries. UI confirms this distinction. Credentials are removed before the record; if saving the record then fails, the error says the credential is already removed and asks the user to repeat the removal or to save the token again through the account-scoped update.
- `refresh_accounts` `{accountId?: string}` → State. Refresh provider names and cached zones, preserving local remarks. An explicit accountId scopes reads to that account. The account management page may explicitly refresh all accounts.
- `refresh_domains` `{accountId?: string}` → State. Read only the chosen account token and zone list; no provider identity, self-test key or monitor key access. A single local account may be selected implicitly, but multiple accounts require a choice before any credential access. Preserve cached zones on authorization, network or persistence failure. Network reads have a 60-second total deadline after system authorization. While another operation holds the backend, the foreground commands (domain, plan, import, account, statistics and self-test commands) wait up to 8 seconds for it; if it is still busy they fail with exactly `上一个操作还没结束，已经等了几秒。请稍后再点一次；如果屏幕上有系统的钥匙串窗口，请先处理它。` The frontend recognizes the opening words `上一个操作还没结束`; the text never contains `令牌`, `凭据`, `授权` or `权限`. UI keeps a separate in-flight guard through edits and dialog close/reopen, and reports progress/success/errors inside the domain dialog.
- `prepare_domain` `{ input, prefix, accountId?: string }` → `{ host, prefix, candidates: { accountId, label, zoneId, status }[], checks: DomainCheck[], canApply, plan?: Plan }`. Resolve an exact hostname without silently stripping www. If more than one candidate exists, list all and require explicit account selection. Only active zones qualify. DNS must be proxied. Probe both prefix root and a random child without following redirects; HEAD may fall back to a bounded GET when unsupported. HTTP 404 passes. HTTP 2xx/3xx and origin/server 5xx responses require explicit directory takeover confirmation; they do not prove the path is unused. Access restrictions, rate limits, other unsupported responses, connection failures, ownership errors and overlapping Worker routes block a plan. `canApply` means no blocking errors, not that every check is green. One hostname and one directory per plan; users can add www separately. No website files, DNS records, redirect rules or firewall settings are changed. When the cached zone ID answers HTTP 404 (the domain was deleted and added again in Cloudflare, so its ID changed), the backend refreshes that account's zone list once, matches the domain again and continues with the new zone; `candidates` then reflects the refreshed list. If the domain is still not found, the `云端域名归属` check has reason `zone_cache_stale` and the message `本机的域名列表过期了，已刷新仍未找到这个域名。请到 Cloudflare 确认这个域名还在所选账户里，再检查一次`, which does not point at token permissions. A confirm-time review that meets the same 404 does not refresh; it fails with `本机记的这个域名的编号已经过期，请重新检查域名`.
- `prepare_domain_dns` `{input,accountId?:string}` → `{host,candidates,checks,dnsStatus,actions,canApply,plan?:Plan}`. Status is `ready`, `missing`, `dnsOnly`, `unsupported`, `conflict` or `readFailed`. Actions describe an exact host record creation or proxy enablement. A missing, mismatched-account, or inactive cached zone triggers a read-only refresh of the selected account before preparation. If a matching cached account or single local account cannot determine the scope, require explicit account choice without reading credentials. A cached zone ID that answers HTTP 404 gets the same single refresh as in `prepare_domain`, with the same final message when it does not help. Failed reads must not be treated as missing ownership. Only a reviewed plan may change DNS. A host with no A/AAAA/CNAME may use a proxied AAAA placeholder; existing MX/TXT/CAA records are preserved and included in the reviewed DNS snapshot. Compare configuration fields (including TTL, MX priority and structured data) in both exact-host and full-zone reads; any observed mismatch blocks the write. Cloudflare does not provide an atomic read-and-create operation, so the application cannot eliminate changes made after its final read. Unsupported records, NS delegation and wildcard conflicts remain blockers; enabling proxy preserves existing record content. Check delegation, wildcard and incompatible records; reread zone ownership and the DNS snapshot before writing. Partial or uncertain writes remain reported for recovery; do not automatically delete or overwrite records to compensate. If a later check confirms ownership and ready DNS, clear only that host’s resolved local DNS journal; preserve it when persistence fails. A successful DNS plan does not bind the domain: prepare the directory again and obtain any takeover consent separately. DNS editing requires the token’s DNS edit permission.
- `prepare_change` `{ kind, ...fields }` → Plan. Kinds: `save_link` `{domainId,slug,cnUrl,defaultUrl,createOnly?}`; `delete_link` `{domainId,slug}`; `remove_domain` `{domainId}`; `cleanup_account` `{accountId}`; `recover_account` `{accountId}`; `rotate_selftest` `{accountId}`. `createOnly` is an optional boolean: true rejects an existing name during preparation and application; missing/false preserves existing edit behavior. The UI sends true for new links, including creating a new name from an existing link; the old link remains unchanged. Cloud/local consistency guards still apply. Recovery discovery must stay read-only; rotating a lost selftest key is a separate confirmed write. Saving an existing link replaces it at its current list position (older duplicates of the same domain and name are dropped); a restored failed delete keeps its position. A later successful save or delete of the same host and name clears that link's earlier `保存链接 {host} / {slug} (`… and `删除链接 {host} / {slug} (`… journal entries in the same commit; link saves and deletes never clear domain journals. A successful domain add clears that host's earlier `添加域名 {host} (`… and `添加域名 {host}（`… entries, a successful domain removal clears that host's earlier `移除域名 {host} (`… entries, and a successful `recover_account` clears every `添加域名` / `移除域名` / `保存链接` / `删除链接` entry whose host lies in that account's current zones (and is not a local domain of another account), all in the same commit as the change. Entries that may be the only place naming cloud resources are never cleared automatically and stay dismissable by hand: entries containing `本次建出的云端资源没能全部撤销`, and every new-account add-domain entry (the part before `：` starts with `添加域名 ` and contains `（计划 KV `), whatever its note says (none while the KV is being created, `已建 KV，正在上传 Worker`, `已建 Worker，正在写资源清单`, `云端结果不确定，需要人工核对`, `失败且回滚未完全成功，需要人工核对`, …); a new-account run whose undo finished ends its entry instead. A save whose cloud value already equals what it would write (ignoring `updated`), for a new name or an edit, is treated as already saved: local state is updated and that link's earlier entries are cleared without another write; a different cloud value keeps the existing recovery guard. An uncertain link write is read back at once and counts as saved only when the value is exactly the one written. A removal deletes the links first, then `c:{host}`, then the route, and a retry continues from wherever it stopped. With the ownership check passing (config and route still there), a cloud `l:{host}:` key that this computer does not list for the domain refuses the removal before any write (`云端链接清单与本机不同，请先找回再移除`). Otherwise the removal goes on, with or without an earlier `移除域名 {host} (`… entry: the key list is used only for that refusal, and what to delete is read key by key from this computer's own list (a key that reads as absent is skipped), so fewer cloud keys than local ones (an earlier removal that stopped while deleting links, links deleted from another computer) or a key list that lags behind a recent save or delete neither leaves a link behind nor stops the removal. On this path an uncertain link, `c:{host}` or route delete keeps the journal (`链接删除结果不确定`, `前缀配置删除结果不确定`, `路由删除结果不确定`) and the error ends with `再点一次「移除域名」会接着做完`, because the next removal continues from there; a definite failure is rolled back as before and its error has no such ending. Removing a domain whose earlier removal stopped after `c:{host}` was deleted (no `c:{host}` in the cloud, verified resource source) does not fail on the missing prefix config or the missing route; this read-only check runs only after those two ownership errors (`云端域名配置已丢失`, `Worker 路由已变化，请刷新或找回`), any other failure such as a failed read is returned as it is without further reads. `l:{host}:` keys may be left only when every key belongs to this domain's local links (for example a refused route delete whose rollback could not put the config back); a key this computer does not list keeps the original error. No earlier `移除域名 {host} (`… entry is needed here, so an entry cleared by hand never leaves a domain that can neither be removed nor recovered. The remaining link keys are deleted first (HTTP 404 counts as gone), then the recorded route when it still exists with this account's Worker as `script` and the domain's `{host}/{prefix}/*` pattern (HTTP 404 counts as gone; when it no longer exists nothing is deleted), and the local domain and its links are then removed with earlier `移除域名 {host} (`… entries. An uncertain link or route delete keeps the journal and the error ends with `再点一次「移除域名」会接着做完`; a definite failure reports the error, ends only this attempt's journal and keeps the earlier entry. A recorded route that now has another script or pattern keeps the original error. `recover_account` skips a route of this Worker that has no `c:{host}` (what an interrupted removal leaves) instead of stopping, and recovers the other domains, after listing `l:{host}:`: when links of that host are still there, and the host is a local domain of this account, recovery stops without changing local data with `域名 {host} 的转发规则还在，但前缀配置已经不在，云端还留着它的短链接。为了不丢本机记录，这次没有找回。如果这个域名本来就是要移除的，请到「域名管理」对它再点一次「移除域名」；否则请联系维护的人`; a host this computer does not list for the account has nothing local to lose, so its route is skipped like one without links. Two routes of this Worker for one host stop recovery, also without changing local data, with `域名 {host} 上有两条本工具的转发规则（{first pattern}、{second pattern}），没法确定该用哪一条，所以这次没有找回，本机记录没有改动。请联系维护的人处理`; other invalid routes keep `此 Worker 的路由无效或主机名重复，停止找回以保留现有记录`. An account cleanup that already has a `清理账号 {accountId} (`… journal and whose Worker settings answer HTTP 404 resumes without the source check: it lists the account's KV namespaces and, when the recorded namespace is still listed, lists its key names first: only the manifest, `m:monitor:cursor`, `h:<id>` and `p:<id>` keys may be present (the same name rule as a first cleanup), and any `l:`, `c:` or unknown key stops the cleanup before any delete with `云端跳转服务已经删除，但这个账户的云端存储里还有链接或域名记录，为了不误删没有动它。请联系维护的人核对后处理`; otherwise the namespace is deleted (HTTP 404 counts as gone). It then deletes the local self-test key (absence is success), clears the local resources and pool receipts and ends the journal. Without such a journal a missing Worker still stops cleanup. The cleanup journal is written before the first delete. When this run wrote it (no earlier `清理账号 {accountId} (`… entry) and nothing in the cloud has been deleted yet, a failure ends the journal instead of keeping it and the error says `云端没有删除任何东西`: a failed or changed re-read of the monitor data, a definite (not uncertain) refusal of the first monitor-data delete, or a definite failure of the Worker delete when it is the first delete. A journal resumed from an earlier run is kept. A Worker delete whose connection never opened (`network` with a definite outcome) is never described as refused: the note says the service was not deleted because the cloud could not be reached, and the error ends with the retry hint. Cleanup errors that a later cleanup can finish end with `再点一次「删除云端短链接服务」会接着做完`: an uncertain or unconnected Worker delete, a failed or changed monitor-data re-read and a failed monitor-data delete that keep the journal, every KV step after the Worker is gone, and a failed local self-test key deletion after the cloud is clean. A definite refusal of the Worker delete after earlier deletes keeps the journal (`Worker 删除被拒绝，账号清理尚未完成`) and returns the Cloudflare message. A cleanup stopped by a route that still points at the account's Worker (for example the leftover that recovery skipped) names the route pattern and the way out: recover the account and remove the recovered domain, or add that host with the same directory again and remove it, then repeat the cleanup. Account cleanup also accepts `p:<id>` platform copies whose value is readable and whose ID still exists in the local platform library; they are re-verified like other records but are removed only with the namespace, never key by key, so a failed later step cannot leave a synced platform address without its copy; any `l:` record, unknown key or unverifiable copy still stops cleanup before any delete.
  - `dismiss_pending_operation` `{entry}` → Plan titled `清除待处理记录`, steps start with `只从本机删除这条记录，不改动云端`, warning `请先确认这条记录对应的云端状态已经核对过`. `entry` must be the exact text of a `pendingOperations` item. Preparation and apply both fail with `这条记录已经不在了，可能已经被自动清掉。请点一下「刷新数据」看最新情况` when no item matches exactly. Entries that still have their own recovery entry are refused with a message naming it: entries matching the journal of a pending platform-address change, monitor change, self-test rotation or Worker upgrade, `重置自检密钥 {accountId} (`… of an existing account, and `清理账号 {accountId} (`… of an existing account that has recorded resources and no local domain. The resume buttons are named as they appear in the bar above the page content on every page (titled `有 N 项变更可继续处理`), for example `这条记录有专门的处理入口，不能直接清除。请用页面上方“……项变更可继续处理”那一栏里的「继续同步」按钮处理`. A `清理账号 {accountId} (`… entry of an account that currently has at least one local domain, or no recorded resources (removed from this computer and imported again), may be dismissed: the cleanup itself refuses to run in that state, so there is no other way out. Apply removes only the first exactly matching item and persists; it reads no credentials and makes no cloud request.
- `apply_plan` `{ planId, acknowledgeDomainTakeover?: boolean, acknowledgeCredentialMigration?: boolean }` → State. A domain plan carrying `domainTakeoverConfirmation` requires the matching explicit acknowledgement; other plans do not gain a bypass from this flag. Revalidate ownership/state and domain path risks before any write, reusing the plan’s server-generated random child path so an echoed redirect URL stays comparable. The client cannot choose this probe path. Newly required takeover consent, materially changed warning observations, or any blocking error require a fresh check; a warning that resolves to 404 is safe. Keep the hostname, directory and account fixed to the prepared plan. Serialize writes, record recovery journal, compensate changes made by this operation only. Distinguish failure, uncertain network outcome, and propagation delay. If the confirm-time review of a domain plan has errors and every error carries a transient network reason, the backend waits about one second and repeats the whole review once. If only transient network errors remain and the plan has not expired meanwhile, the error text contains the exact marker `接入计划仍然有效` (`网络检查没有完成（{label}：{message}）。接入计划仍然有效，云端没有任何改动，可以直接再点一次确认。`) and the plan is put back unchanged (same `id`, expiry and local snapshot), so the client may confirm the same `planId` again. The marker is present exactly when the plan was kept: if the plan ran out while the review was in progress it is consumed and the text ends with `这份接入计划已经过期，云端没有任何改动，请重新检查域名。` instead. The marker is only returned before any recovery journal, local state change or cloud write. Any other review failure returns `复核没有通过（{label}：{message}）。云端没有任何改动，请重新检查域名。` naming the first non-network error, and the plan is consumed. Other plan kinds and other errors keep single-use behavior. For path-risk comparison, origin failures match when both are 5xx (for example 522 then 521). Adding the first domain to an account without local `Resources` first lists its KV namespaces and reads their ownership manifests (the same filter as recovery discovery) before any journal or write: an owned manifest blocks the write and points to account recovery, a namespace without a manifest is not a blocker, and a failed list or read fails closed. Each owned manifest's Worker is probed read-only: when it no longer exists (HTTP 404) recovery cannot succeed, so the error names the leftover namespace and Worker and asks the user to review and delete that namespace in Cloudflare instead of pointing to recovery; any other probe failure fails closed. For an account with local `Resources`, leftovers of an earlier unfinished add are recognized, where this tool's route means `script` equals the account's Worker and `pattern` equals `{host}/{prefix}/*`: a `c:{host}` with no route of this Worker for that host is checked against the account's `l:{host}:` keys before anything is written (still before the journal): a failed list returns its error and writes nothing; with no keys the config is reused when its prefix matches and overwritten otherwise; with keys and the same prefix the add goes on, and after the domain was added the add-domain entry is kept with the note `云端还留着这个主机名以前的 {n} 条短链接，现在重新生效了，本机列表里还看不到。请到该账户的「管理账户」点「从 Cloudflare 找回配置」把它们找回来` instead of being ended (recovery settles it like any add-domain entry of the account's zones); with keys and another stored prefix it refuses without writing (`云端还留着这个主机名以前的 {n} 条短链接，它们用的链接目录是「{old}」。请把链接目录改成「{old}」再添加；本次没有做任何改动`), and with keys and an unreadable stored config it refuses and asks to contact the maintainer. This tool's exact route without `c:{host}` passes the preflight route check (`发现本工具上次没做完留下的转发规则，接入时会直接沿用`) and is adopted instead of creating another; before anything is written the account's `l:{host}:` keys are listed (an interrupted removal whose config rollback failed may have left them): a failed list returns its error and writes nothing, and with keys the add goes on and its entry is kept with the same `云端还留着这个主机名以前的 {n} 条短链接…` note. A plain first add (no `c:{host}` and no route of this Worker for the host) does not list keys. A route of this Worker for exactly this host under another directory (pattern not `{host}/{prefix}/*` for the requested prefix) is what an interrupted removal leaves; another route for the same host would make recovery fail: the preflight route check reads `c:{host}` (present: the recovery message below; absent: error `这个域名上还留着本工具以前建的转发规则 {pattern}（上次移除没做完）。请把链接目录改成「{old}」再检查，添加时会直接沿用它`; a failed read: a read failure like the neighbouring checks), and confirm refuses the same way without writing when the config is absent and no route of this Worker for the host is the exact one. Config and a route for the host together without a local domain still require account recovery (the message names the “管理账户” / “从 Cloudflare 找回配置” entry); any other overlapping route remains a conflict. An uncertain `c:{host}` write is read back (identical value: continue; absent: definite failure with rollback, `这一步没有收到明确的答复，查看后发现前缀配置没有写进云端，请再试一次`; unreadable: stays uncertain), and an uncertain route creation lists the zone's routes (this tool's exact route: adopt its ID; none: definite failure with rollback, `这一步没有收到明确的答复，查看后发现转发规则没有建成，请再试一次`; unreadable: stays uncertain). "Uncertain" includes HTTP 5xx and 408, so these texts do not claim a network cut. When a new account's KV creation, Worker upload or manifest write is uncertain, the backend tries to delete what this run may have created (Worker, and the KV by ID or by its planned title; 404 counts as gone): if everything is gone it ends the journal, removes the staged self-test key and returns `这一步没有收到明确的答复，已撤销本次创建，请再试一次`; otherwise the journal stays uncertain and names what may be left, and the error says the names are in 「查看待处理记录」 above the page. Domain setup confirms that the cloud configuration was saved; actual redirect behavior is checked after creating a short link. Existing Cloudflare redirects or access policies can still take precedence.
- `selftest_link` `{domainId,slug}` → `{status:'passed'|'pending'|'failed'|'key_missing',message,checks:Check[]}`. Sign both CN and US probes, do not follow redirects, compare exact status and Location; no target reachability claims. Bound retries. A region check that still ends on a transient network reason (see `DomainCheck.reason`) makes the result `pending`, never `failed`, with a message that says the network did not connect rather than that the edge is propagating. While the account's self-test key update is unfinished, `key_missing` says so and points to that account's button in the pending area (`继续修复`, `查看修复计划` or `找回本机检测配置`) instead of to resetting the key.
- `check_link_redirect` `{domainId,slug}` → `{status:'passed'|'failed'|'unknown',message,reason,checkedAt,dnsMode:'system'|'public'}`. Anonymous first-hop HEAD only, derived from one unambiguous current local domain/link/platform snapshot; no credentials, Cloudflare API calls, GET fallback, redirect following, response body reads, or cloud writes. A matching 302 Location proves only that this network exit returned a configured target (official or enabled regional candidate); it does not prove region selection, fallback priority, or target-site reachability. Missing/mismatched Location and explicit 404/410 are definite check failures; unsupported methods, challenges/rate limits, network failures and 5xx are unknown. Exception: a 503 carrying exactly one `X-Reason` header (set by the Worker on its own 503s) is `failed` with reason `worker_pool_missing` (`pool_missing`: the platform address is missing in the cloud), `worker_no_candidate` (`no_candidate`: every mainland candidate is unavailable) or `worker_internal` (`internal`: the Worker failed); the message says visitors cannot open the link now and, for the first two, points to the 「平台地址」 page; for `pool_missing` it says to click that pool's 「编辑地址」 and save it once without changes, which writes the cloud copy again (see platform saves below). Any other header value keeps the plain 503 behavior. Reuse the public-address-pinned HTTPS client; only an identified VPN virtual-DNS answer allows one public-DNS retry, within a total 20-second deadline. Never return remote target/header/body contents in diagnostics. A separate single-flight gate rejects overlapping checks. Taking the local snapshot may wait behind another operation, including a cloud mutation, for at most 10 seconds and otherwise returns reason `busy`; the probe itself runs without holding the backend.
- `export_config` `{}` → JSON string without secrets. UI saves via native dialog.
- `import_config` `{json}` → State plus a one-off `configImportReport: { domainsAdded, linksAdded, poolsAdded, linksExisting, linksDiffering }` that is never persisted. Import non-secret local configuration after schema validation and remote ownership/read checks; never accept credentials or injected route/resource IDs as authoritative. No remote writes. The import is all-or-nothing: any entry that is missing locally, missing in the cloud or different from the cloud rejects the whole file, and the error names the account (local label when known, plus the last characters of its ID), domain (`host/prefix`), link (`host/prefix/slug`) or platform address. Existing local links with the same domain and name are kept unchanged; `linksExisting` counts them and `linksDiffering` counts those whose local content differs from the cloud value just verified.

Backend persists credentials in the OS key store and non-secret state in app data, never the project tree. Successful secret reads may be reused in Rust memory with a 30-minute sliding idle deadline and an 8-hour absolute limit from the system read/write. Missing-item results may be cached for 5 minutes without secret data. Per-key loading coordination, invalidation on mutation failure, successful mutation replacement and clearing on window close or exit remain required. Missing credentials are distinct from denied/cancelled access. No system password is collected by the application.

On macOS, ordinary credential access uses the bundled credential helper. The helper authenticates the calling application by its fixed identifier and signing certificate; the application verifies the helper's identifier, certificate and architecture-specific code hash. The helper archive is immutable across application-only updates and must retain its exact signed bytes through app, disk-image and updater packaging. Rebuilding the main application must not rebuild or re-sign the helper. Initial or changed system authorization can still require a user decision; tests must distinguish a successful credential read from observed absence of a system prompt.

Both processes resolve the user's default Keychain without changing its location, search list, trust or access controls. Location resolution failures are not missing credentials. A location change invalidates cached and in-flight values and fails closed, including after a native operation; rejected internal plaintext is cleared before release. The helper permits only one active credential operation globally and rejects concurrent callers without queuing another system prompt. Cancellation or timeout is not permission to replay the operation. Windows continues to use its native credential backend independently of the macOS helper.

### Local macOS credential migration

`prepare_change` also accepts `{kind:'migrate_credentials',accountId}`. Preparation reads local metadata only and returns a single-use plan with `credentialMigrationConfirmation`. Applying this plan additionally requires `acknowledgeCredentialMigration: true`; expired, replayed or stale plans and missing acknowledgement must fail before accessing credentials. Windows does not offer this migration.

Ordinary macOS credential operations use the fixed `org.shortlink.generator.credentials.v2` service. Legacy accounts require an explicit migration before ordinary credential reads or credential-dependent mutations; local viewing, renaming and label-only backup imports remain available; this condition is distinct from a missing credential. A v2 access failure never falls back to the legacy service. Merely opening the application, refreshing local state or preparing the migration must not trigger a legacy read. The account's local migration marker is not exported or accepted as backup authority. Backup schema remains version 1; its account entries accept only `id` and `label`, and reject migration markers.

Migration processes the exact account's token, self-test, optional probe and pending self-test credentials. It preserves existing v2 entries, copies legacy entries with create-only semantics, checks duplicate races without overwriting, and reads back directly from the backend rather than the cache. Denial or failure stops subsequent reads. The account marker is committed only after all kinds have been accounted for and the token is readable; persistence failure leaves the account gated and preserves any copied entries for an explicitly confirmed retry. Migration never changes cloud secrets or recovery journals, deletes legacy entries, or changes their ACLs. Updating a token alone must not mark the other legacy credentials as migrated.

Recovery and multi-account writes must check migration requirements before changing journals, generating keys or performing cloud mutations. Successful migration does not automatically resume a pending cloud operation. Local account removal deletes current credentials only; retained legacy entries are not implicitly deleted, and their values may become stale after later updates. A new process after normal application exit must be tested independently: cached reads cannot establish persistent access.

`check_link_targets` returns local checks with `status`, `message`, `source`, `url`, `checkedAt`, `reason` and `stage`. Reason/stage explain DNS, transport, redirect or HTTP outcomes without weakening public-address validation. Local target and redirect checks disable application HTTP proxies, not OS routing; they never establish Mainland reachability. `check_link_targets`, `selftest_link`, and `prepare_domain` accept optional `dnsMode` (`system` by default, or explicitly selected `public`; other values are rejected). Public mode queries a fixed Cloudflare HTTPS DNS endpoint with pinned bootstrap addresses, normal certificate verification, no redirects and bounded answers; only hostnames and record types go to the resolver. One process-wide resolver reuses its connection (4-second connect, 6-second request, 7-second attempt limits). Only `public_dns_timeout`/`public_dns_failed` are retried, at most three attempts within 12 seconds; definitive results are not retried. Successful answers (IP addresses only) are cached per hostname for 60 seconds in a bounded cache and revalidated on every use; concurrent lookups of the same hostname share one query pair. Both A and AAAA must succeed. Target connections pin validated public IPs while retaining the original hostname and TLS verification. Every destination redirect is revalidated; mixed private/public or virtual answers fail closed without fallback. Reports identify the DNS mode. Domain plans retain their selected mode and recheck the same random path before execution; execution payloads cannot override that mode. No-response errors still block domain attachment, while received 5xx responses retain explicit takeover confirmation. Cloudflare API authentication uses its unchanged separate client. Its GET/HEAD reads (including KV value and Worker content reads) are repeated at most twice (after about 0.3 s and 1 s) only when no HTTP response was received; writes are never repeated on a lost response and remain reported as uncertain. Self-test probes retry transient network reasons within their existing attempt loop and report the real reason when every attempt failed on the network. Exported files contain the user's domains and targets and are private backups. Preview mode must be explicitly labeled and never persist real tokens or call cloud APIs. No cloud writes are permitted during implementation without a separately supplied test hostname and credentials.

## Edge storage

Worker binding `LINKS`; secret `SELFTEST_KEY` is 64 hex characters representing 32 random bytes. HMAC SHA-256 uses decoded raw key bytes and UTF-8 message `host|path|unixSeconds|country`; request header `X-Selftest: seconds.COUNTRY.lowercaseHexSignature`, tolerance 300 seconds.

`c:<host>` contains `{prefix}`. `l:<host>:<slug>` contains `{rules:[{countries:['CN'],url}],default,updated}`. Internal recovery manifest may use `m:config` and must be checked against Worker bindings and zone routes before accepting ownership. Public responses carry no product-identifying headers; the Worker's own 503s carry a neutral `X-Reason` header, described below. Script source lives in `edge/worker.mjs` and is embedded by Rust at compile time.

Prefix `[a-z0-9-]{1,12}`. Slug `[A-Za-z0-9_-]{1,32}`. Redirects use only saved absolute HTTPS URLs. Worker handles GET/HEAD, rejects other methods, matches an exact prefix/slug path, ignores incoming query strings, defaults missing or unknown countries to default, and never fetches the destination. Before matching, the Worker drops trailing punctuation (`. , ; : ! ? ) ] } ' "` and `。，；：！？）】》」』”’、`, literal or percent-encoded), one trailing `/`, then trailing punctuation again; name characters are never removed, a dot segment such as `/..` is not treated as punctuation, and the raw path may be at most 128 characters. Selftest signatures, rate-limit keys, click statistics and case fallback all use the normalized path; a path that still does not match is 404. Responses have no product-identifying headers; the Worker's own 503s carry a neutral `X-Reason` header: `pool_missing` (platform address absent from KV), `no_candidate` (mainland visitor and every backup address unavailable) or `internal` (any other caught failure). Other responses, including the 503 for a missing `LINKS` binding, carry no reason header. KV cache is bounded in size and TTL; authenticated probes bypass process cache. KV propagation delay is not a reason to delete a successfully saved resource.

## Startup

If local startup fails (another copy holds the configuration lock, the configuration cannot be read or parsed, or another load error), the application hides its window, shows an error dialog and exits after it is closed instead of crashing. The app is called `短连接生成器` in the Dock and the window title and `短链接工作台` inside the window, so the dialog title is `短连接生成器没能打开` and every text starts with `短连接生成器（窗口里叫“短链接工作台”）`, naming both once. The text depends on the cause: another copy running (`…已经开着了，请切换到已打开的窗口；如果找不到，请退出后重新打开。`); a credential format version this build does not support (written by a newer version: names the cause, says the configuration file was not changed, suggests installing the latest version, then contacting the maintainer); an unreadable or invalid configuration file (names the cause, says the file was not changed and that reinstalling does not change it, and asks to contact the maintainer; no reinstall suggestion); or the original cause after `…没能打开：`.

## Application version

`State.appVersion` and every `check_update` result’s `currentVersion` come from the running binary’s package version, not stored user configuration. An available update additionally reports `version`. The UI shows the current version even when the update channel is unavailable. Version metadata is not persisted into user backups.

Once local startup succeeds, the client quietly checks update metadata after five seconds, then at most once every six hours while visible or when returning to the app. Automatic checks never access account credentials, download or install software, open a dialog, or interrupt work on failure. The check runs outside the account-operation lock. A detected release keeps a sidebar badge and a dismissible top reminder; closing its details does not discard the sidebar reminder. Manual checks share an in-flight request and may retry immediately after a failure. Installation remains explicit and exclusive with backend mutations. Only `install_update` returning `status:installed` is displayed as installed; `up_to_date`, `unavailable` and failures cannot claim installation success. After installation the running binary version remains unchanged until restart, and the client retains a restart reminder without repeatedly checking the old binary.

- `check_update` `{}` → `{status:'unavailable'|'up_to_date'|'available',currentVersion,version?,notes?,message}`. This reads metadata only. `version` and optional `notes` describe an available release.
- `install_update` `{}` → the same unavailable/up-to-date results, or `{status:'installed',currentVersion,version,message}` after installation succeeds; failures reject with a sanitized string. It rechecks metadata, downloads, verifies the signature and signed version, then enters installation. One backend install attempt may be active at a time; overlapping attempts reject instead of queuing. Downloading does not hold the account-operation lock; the final installation uses the exclusive backend lock and waits up to 30 seconds for a running operation before it fails with the busy message.
- `cancel_update` `{}` → `{status:'cancel_requested',message}` before the install boundary, including when no attempt is active. This acknowledges a cancellation request, not completion of the original `install_update`. The caller keeps that attempt in flight until its promise settles; a cancelled attempt rejects with a cancellation message and releases its gate. Cancellation can stop metadata/download waits or prevent entry to installation, but does not interrupt synchronous verification. Once the backend atomically commits to the install stage, cancellation rejects, even if the next progress event has not yet arrived; filesystem installation and its final signature check must complete or fail normally.

During an install attempt, the application emits `update-progress` with `{phase:'checking'|'downloading'|'verifying'|'installing'}`. These are stage notifications, not percentages or terminal results. Not every attempt reaches every stage; missing update configuration, no newer release, cancellation and failures can end early. The settled `install_update` result remains authoritative, and the UI must not infer success from a progress event.

Both metadata and artifact requests use HTTPS with normal certificate validation, reject URL credentials and allow at most five HTTPS redirects. Metadata is streamed with a 1 MiB response limit, a 30-second total deadline and a 10-second idle deadline; artifacts use 256 MiB, ten minutes total and 30 seconds idle. The shared client has a 15-second connection timeout, additionally bounded by the applicable total/idle deadline. A declared Content-Length above the limit rejects before buffering; each received chunk is checked against the cumulative limit even without that header, and a supplied length must match the final bytes. The limit applies to the bytes delivered by the HTTP client, including decoded bytes if decoding is enabled. Empty, malformed, oversized, truncated or timed-out metadata rejects without installation; HTTP 204 means no update. Only bounded server metadata reaches the official updater's version comparison and platform selection, never client-supplied IPC metadata. Cancelling an install attempt during metadata retrieval drops that read and releases the attempt gate. These are implementation requirements, not a claim that a candidate installer has passed native release validation.

Domain onboarding may automatically chain read-only preparations when DNS is the sole blocker, but every DNS repair and directory takeover requires its own explicit plan confirmation. A failed DNS write retains the draft and visible recovery actions; retrying after a permission change only prepares a new plan, never applies it automatically. Destination validation rejects port zero and addresses longer than 2048 characters after URL serialization, before preparing or applying writes.

Platform definitions form a workspace-wide library. `Pool.accountIds` is an internal deployment receipt list, not an access-control list. New definitions can be saved without any connected account. Link preparation accepts any saved platform and discloses automatic setup for the selected domain account. On first use, the backend verifies domain/resource ownership, checks for conflicting cloud values, records resumable intent, and syncs the platform plus any existing monitor list before writing the link. It reads no unrelated account credential during first use. Platform edits preserve deployment receipts and accounts referenced by existing links; callers cannot remove these recipients through the form. Partial setup must keep a resumable operation and must not report the link as saved. A definite refusal of the first platform write (not uncertain) rolls back this operation's journal, pending change and receipt in one commit; an uncertain result keeps them. The same holds for a fresh platform save (`save_pool`, not a resumed sync) whose first account write is refused, restoring the previous local version, and for a fresh monitor start whose first write (the Worker probe secret) is refused; the error then says the cloud is unchanged. Once any write of the operation went through, or on a retry of an unfinished operation, the records stay for recovery. A `p:<id>` missing in the cloud of an account whose local status is synced is not a conflict: `save_pool` writes it like any account without a copy (nothing can be overwritten because nothing is there), so editing the pool and saving it without changes re-creates the copy; preparing a save does not refuse unchanged content. Saving a link that uses such a pool refuses without writing and names that way out: `这条链接用的平台地址在云端的副本不见了。请到「平台地址」页点这组地址的「编辑地址」，不用改内容，直接保存一次，再回来保存链接`. `delete_pool` counts such an account as already deleted.

Self-test key updates use an explicit recoverable transaction. A new key is staged only in the OS credential store before any cloud request, and non-secret intent is persisted with the account and resource binding. `prepare_change` accepts `resume_selftest_rotation` for staged transactions and `recover_selftest_rotation` for legacy failed operations or transactions whose staged key is missing. Both require explicit confirmation. No background recovery or retry runs after an operation returns failure; bounded HTTP 429 handling within the confirmed request remains in effect. Pending rotation makes the account require key recovery and blocks self-test results until repaired. Cloud-applied transactions resume local key promotion without another cloud update. State, plans, journals and backups must never include secret values; destructive account/resource operations must not discard an unresolved rotation.

For an account with a legacy self-test journal but no local `Resources`, `prepare_change` accepts `{kind:'recover_selftest_resources',accountId}`. Preparation is local-only and returns an explicit, single-use, expiring plan. Apply checks the credential migration gate and conflicting operations before accessing credentials, then uses read-only cloud discovery to find exactly one account-bound, validated manifest/namespace/Worker/source match. Unknown journals and unreadable candidates are blockers, not evidence of absence. The operation persists only the target account's `resources` and `hasResources`; secrets, business data, other accounts and recovery journals remain unchanged. A discovery or persistence failure must leave local state unchanged. Success offers a separate self-test recovery confirmation; it must never rotate a key, clear a journal or automatically prepare/apply a subsequent operation. Ordinary account recovery retains its existing pending-operation guard.

### Link-name case compatibility

New link names use lowercase ASCII. `prepare_change` with `kind:'save_link'` retains the exact name of an existing link when editing it; otherwise the name is normalized and checked for a case-insensitive collision in the same host. `createOnly:true` must never overwrite an existing name, including a case variant. Apply repeats the local check and, for new names only, performs one complete cloud key-name preflight before writing. A failed or incomplete preflight blocks the write. This check is not an atomic cross-client lock. Configuration import and recovery preserve historic exact keys, including distinct legacy `OK` and `ok` entries. Destination URLs, referral codes and directory prefixes are not normalized.

The current Worker tries an exact name first, then its lowercase exact key, then a unique legacy case-folded name. Multiple legacy candidates with no lowercase exact key return 404 for a non-exact spelling. This preserves previously shared exact URLs. Legacy fallback lists only the requesting host's link names. It accepts only complete, bounded scans (20 pages), caches indexes for ten minutes with host/name limits, and shares concurrent scans. Per binding and isolate, it allows at most six scans and 24 list calls per hour. List failures, exhausted budgets and incomplete scans disable only this fallback; exact matches continue normally. These are isolate-local limits, not an account-wide free-quota guarantee. Authenticated self-tests bypass the index cache while remaining subject to these limits.

Updating the desktop app does not silently deploy a new Worker to existing accounts. `prepare_change` accepts `upgrade_worker` for an explicit, expiring, single-use account upgrade plan that lists affected imported domains. Apply validates the owned manifest/source, preserves approved compatibility settings, namespace and secret bindings, and checks the source, settings and schedules after upload. A non-secret pending transaction is persisted before the upload. `resume_worker_upgrade` reads the current cloud state and repairs the manifest only after verifying the intended source; it never blindly repeats an upload. A read of the previous source keeps the pending record, even on resume, because it cannot prove the upload did not happen. A definite upload refusal (a 4xx other than 429, or `success:false`) clears this upgrade's pending record and journal in one commit and reports that the cloud is unchanged; 429 and uncertain outcomes keep the record. When other pending work blocks a new upgrade, the error names the first blocking entry and the count; when the blocker is a pending record the text is `请先到页面上方「查看待处理记录」里核对并清除：{first}（共 N 项），再升级此账户的云端跳转服务`, unless that first record has its own entry (see `dismiss_pending_operation`), in which case it is `请先处理待处理记录里的这一条：{first}（共 N 项）。{where to handle it}，再升级此账户的云端跳转服务`. A first record that may be cleared by hand but that one more click usually finishes names that click and still allows clearing: `待处理记录里还有这一条：{first}（共 N 项）。请先{step}；实在做不了，也可以到页面上方「查看待处理记录」里核对后清除它。然后再升级此账户的云端跳转服务`, where `{step}` is `到「域名管理」对域名 {host} 再点一次「移除域名」把它做完` for a `移除域名 {host} (`… record of a host that is still a local domain, and `到「Cloudflare 账户」页打开账户「{label}」的「管理账户」，点「从 Cloudflare 找回配置」把那些短链接找回来` for an add-domain record of a local host whose note says earlier links serve again. Any pending record still blocks upgrades of every account. Pending work blocks conflicting changes for that account. `dismiss_worker_upgrade` requires a separate confirmation and only releases the local pending record, without modifying the cloud or secrets. Source ownership and integrity checks remain in effect after dismissal; externally modified services still require manual reconciliation. Missing secret bindings after a verified upload are surfaced through the existing self-test/monitor recovery status rather than leaving an inescapable upgrade record.


### Passive click statistics

Click statistics are observational and never gate or select a destination. There is no CAPTCHA, browser script, intermediary HTML page, challenge, alternate destination for bots, or additional visitor request. GET requests that actually receive a successful short-link 302 may emit a non-blocking event; a missing or failing analytics binding must not change the status, Location, headers or body. HEAD, authenticated self-tests, invalid routes, missing links and failed redirects do not contribute events. Spoofing an invalid self-test header cannot exclude a normal GET from statistics.

`CLICK_EVENTS` is an optional `analytics_engine` binding with the sole allowed dataset name `slg_clicks_<owned namespace id>`. New accounts and ordinary Worker deployments do not enable collection implicitly. `prepare_change` kinds `enable_click_stats` and `disable_click_stats` prepare separate explicit account-wide plans listing affected domains. Enabling adds this exact binding and deploys the bundled Worker after ownership, source, configuration and schedules have been verified; disabling removes this binding without changing the current verified source. Secret bindings and existing links are preserved. Existing Worker upgrade journals remain readable. The journal retains both original and intended settings; source and target settings jointly determine success, including when the source hash is unchanged. Resume only verifies and completes the recorded operation, never repeats an upload. An ordinary later Worker upgrade preserves an already enabled exact statistics binding.

Events use `indexes: [host.slice(0,96)]`, `blobs: ['v1',host,prefix,canonicalSlug,classification,trafficKind,reason]` and `doubles: [1,first,repeat]`. The original seven blob fields and v1 event version remain unchanged for older clients; first and repeat are 0/1 indicators and are both zero for preview/prefetch or unmeasured events. `canonicalSlug` is the actual matched KV key name, preserving distinct legacy case-sensitive keys. Classification is `likely_human`, `likely_bot` or `unknown`; traffic kind is `click`, `preview` or `prefetch`. Recognizable link previews and prefetches are reported separately and excluded from ordinary click totals. Absence of a bot marker does not establish a human: positive browser navigation signals are required for the heuristic human category. User-Agent and fetch metadata can be spoofed. Optional Cloudflare bot signals enhance classification when present, but their absence never implies a human. Neither country, VPN usage nor IP reputation alone determines the classification.

Analytics events exclude IP addresses, raw User-Agent, referrers, query strings, destinations and invitation codes. Only aggregate counts are returned to the app. `get_link_stats` accepts `{domainId,slug,days}` with an exact existing local link and days restricted to 1, 7 or 30. Account, dataset, host, prefix and slug are derived from verified owned resources, not arbitrary client SQL or API URLs. Query results use `SUM(_sample_interval)` rather than row count. Reports identify counts as estimates subject to sampling, ingestion delay and provider retention; they are requests, not unique people, and cannot reconstruct clicks before collection was enabled.

The report has `{status,message,domainId,slug,days,queriedAt,estimated:true,totals?}`. Status is `ready`, `disabled`, `no_data`, `permission_denied` or `unavailable`. Only `ready` carries totals `{total,likelyHuman,likelyBot,unknown,previews,prefetches,dedup:{first,repeat}}`. `total` is the sum of the three ordinary-click classes, excluding preview/prefetch events. A valid empty result is `no_data`; a failed read, missing permission or malformed provider response is never presented as zero real clicks. Queries have fixed SQL, bounded response size and row counts, strict category/number checks, and sanitized errors. Reading analytics requires the provider's Account Analytics Read permission; the application never changes the token permissions or requests a wider token silently. Users can edit their existing token in the provider's management page. First use also requires Analytics Engine to be enabled for that Cloudflare account. A provider 401/403 does not prove which prerequisite is missing; guidance covers both the existing token scope and service activation. New-account token templates include Account Analytics Read, while collection remains opt-in.

The statistics dialog is requested by a user clicking a particular link's statistics button; merely starting the application or displaying a long link list does not read statistics or account credentials. Range changes, refresh, cancellation and late responses remain scoped to the selected link; old responses must not overwrite a newer selection. Changes to collection use the existing plan-review flow, and opening the statistics dialog never applies a plan. Local preview data is explicitly labeled as an example and never presented as real analytics.

### Statistics center

`get_stats_center` accepts `{accountId,domainId?:string|null,days:1|7|30,page:number,pageSize:25,readSessionId?:string}`. The account is explicitly selected, the optional domain must be an imported domain in that account, and page is a one-based integer. Identity, account ownership, pagination and bounded query scope are validated before credential access. Empty local scope does not access credentials. Without `readSessionId`, the backend verifies the selected account's credential eligibility, resource ownership/source and exact analytics binding, then makes at most two fixed, bounded Analytics Engine queries: the selected domain scope summary and the current page of exact local links. Both use weighted counts and validate all returned identities and classification groups. A failed query never produces a partial successful report or fabricated zero totals.

The response includes `status`, `message`, `accountId`, `domainId` (null for all imported domains in this account), `days`, `page`, `pageSize`, `totalLinks`, `queriedAt`, `estimated:true` and optional `readSessionId`. Ready reports contain `totals` and `rows:[{domainId,slug,totals}]`, using the same totals and dedup fields as single-link reports. A confirmed empty query is `no_data`, without summary totals, and may include zero rows for current links; an empty local scope is identified separately in the message. Other failure/disabled states omit totals and rows. Rows are sorted by domain ID then slug; the summary includes recorded traffic for deleted links within the selected imported-domain scope, while the table lists only current local links.

A successful verified read (`ready` or provider-confirmed `no_data`) returns an opaque `readSessionId`. This in-memory receipt binds the account, optional domain, days, fixed `pageSize:25` and a digest of the full current local database. It retains the initial summary, `queriedAt` and a fixed UTC query window: timestamps greater than the captured window end minus the selected days, and at or before that end. Its 60-second TTL starts after resource verification and before the initial analytics queries; subsequent pages do not extend it. The backend keeps at most 16 receipts and may evict the oldest. Receipts do not survive restart and contain no token.

Later pages may send the returned ID with the same scope. Each page still validates local identities/pagination, the database digest and credential eligibility, and obtains the selected account token through the ordinary credential cache. It reuses the verified resource/binding receipt and summary, and queries only the requested page when needed. An unknown, malformed, expired, evicted or scope/state-mismatched ID rejects before credential access or network I/O; clients must refresh without an ID to obtain a new read. A provider query or result-validation failure invalidates the reused receipt and returns no successful partial report. Omitting `readSessionId` remains compatible on any valid page and performs a fresh, independently verified read. A fixed time window and reused summary do not make the provider's data atomic: ingestion can change between page queries.

The center defaults to an all-account overview without automatically reading credentials or polling. An explicit overview read calls the existing single-account operation sequentially, including every page needed for current local links in each eligible account, reusing that account's returned `readSessionId` for subsequent pages when supplied. Each page must match the current local count and exact page identities; the local scope bounds pagination. Only the first validated `ready` summary per account contributes to the overview, so reading additional pages cannot duplicate summary totals. Summary totals cover each account's full imported-domain history, including deleted links, while the searchable, sortable, locally paginated all-links table shows current local links across accounts. A partial page failure preserves validated rows and summary, marks the missing detail, and never fabricates zeros. Disabled, empty, failed, migration-required and unread accounts remain explicit. Users can stop the queue; an in-flight response arriving after stop or scope changes is ignored. Reads across pages are not an atomic snapshot. Integer overflow or ambiguous local identities prevent aggregation. A collapsed account summary retains status and current domain/link counts, and permits drilldown using the separately preserved first page of the existing single-account view.

Reading and refreshing remain explicit; switching account, domain, period or page clears old results. Scope/data changes discard late responses and stop the remaining overview queue; an already sent read may still complete. Enabling/disabling reuses the confirmed account-wide change plan. The client distinguishes aggregate estimated request counts from unique people and separates preview/prefetch traffic from ordinary requests.


## Automatic redirect checks

Desktop automatic checks are opt-in and separate from the existing signed regional self-test and target-site checks. Full rounds run serially while the application is open, online and not paused by another operation, approximately every 48 hours. A full round interrupted by a pause, going offline or a `busy` reply is resumed where it stopped: only the links it has not checked yet (plus any whose configuration changed meanwhile) are checked, instead of starting over. Closing the application or sleeping the computer stops coverage. When a round is due after resuming or reopening, one round runs when the gates permit; missed intervals are not replayed. The anonymous HEAD probes do not enter this Worker's GET-only click statistics, but still consume ordinary Worker/network request resources. They check only the first redirect from the current network, without following the destination or proving mainland China or destination availability.

The only persisted monitoring data is the enabled preference and the wall-clock completion timestamp of a nonempty full round in which every current configuration passed and no confirmation or changed-link work remains. Empty lists, interrupted rounds that have not been finished and rounds with failed or unknown results do not write a successful completion timestamp. A resumed round that completes with every current configuration passing does write it, with the time it finished. The UI's last completed full round may include non-passing results and is distinct from this persisted timestamp. Reopening before a valid successful timestamp is 48 hours old avoids repeating that full round; missing, invalid or future timestamps require a fresh round. Per-link results, configuration fingerprints, URLs, tokens and response headers are not persisted. Disabling monitoring clears the successful completion timestamp.

While monitoring is enabled in the current session, added or changed configuration fingerprints enqueue checks only for affected links; removals clear obsolete results and queued work. Scope changes invalidate the persisted completion timestamp. Incremental checks retain the existing full-round deadline rather than postponing it by 48 hours, and do not write a successful full-round timestamp. After a scope change, reopening therefore requires a full round until a new fully passing round has completed. All checks and prioritized confirmations share one serial queue and retain offline/busy and obsolete-response gates. A `busy` reply is not a result: the link stays queued (in its round, the changed-link queue or its confirmation), and all automatic work waits 1 minute, then 3, then 10, then every 10 minutes while replies stay `busy`; the first other reply resets this sequence, and a manual run or disabling monitoring ends the wait. While any link of a round is still waiting, the round is not marked finished.

Within a session, the next full round is due 48 hours after the previous one finished, or, after a resumed round, 48 hours after that round first started, so results from before the stop are rechecked before they expire. Elapsed scheduling advances by the greater nonnegative change in wall time and monotonic time: monotonic progress prevents clock rollback from extending deadlines, while wall time accounts for sleep where the monotonic clock pauses. Focus, visibility and online transitions re-evaluate due work. Reports dated in the future are stale, and freshness also expires after 48 hours plus five minutes of elapsed time. Across restart, only the persisted wall timestamp is available: a clock rollback while closed cannot always be detected if that timestamp still precedes the new current time. These rules provide bounded in-app scheduling, not continuous cloud monitoring.

A first definite failure schedules a prioritized recheck approximately one minute later. Only consecutive definite failures for the same configuration fingerprint confirm a first-hop alert. Unknown responses break the consecutive-failure count and never count as recovery; a previous confirmed alert remains unconfirmed until a passed check. Offline, busy and unsupported responses do not imply the link is broken. Results include check time and cannot remain fresh indefinitely. Changing or removing the link/domain/platform, disabling monitoring or unmounting invalidates late results and queued rechecks. Monitoring alerts and per-link results do not overwrite manual detection results, and do not automatically repair routing or change targets.


### High-frequency protection and estimated deduplication

Fresh owned Worker deployments and explicit upgrades include `CLICK_RATE_LIMITER` (`ratelimit`), with `simple:{limit:100,period:10}`. The positive account-local namespace is derived deterministically from the owned KV namespace. The only accepted opt-out is `CLICK_GUARD_DISABLED` (`plain_text`, text `1`); ordinary upgrades and statistics activation preserve it. Provider default `mitigation_timeout:0` is normalized away; other configurations are rejected rather than silently widened. `get_click_protection` is an explicit read of an owned account and returns `{accountId,status,limit:100,periodSeconds:10,checkedAt}`, where status is `enabled`, `disabled` or `upgrade_required`. Opening account management does not itself read credentials. `enable_click_protection` and `disable_click_protection` use the existing single-use plan and recoverable Worker-upgrade transaction. Enabling uploads the reviewed bundled source; disabling only adds the opt-out binding and preserves the current verified source.

After route validation and valid authenticated self-test exclusion, normal GET/HEAD requests are limited before KV reads by a domain-separated keyed digest of Worker scope, host, prefix, folded slug and available `CF-Connecting-IP`. Query strings and User-Agent cannot create new limit keys. Excess traffic receives a temporary 429 with Retry-After, no CAPTCHA or interstitial. Limits are approximate and local to a Cloudflare location; shared egress IP traffic can aggregate. Missing/invalid identity, absent limiter, error or a bounded limiter timeout permits the original redirect path. This protects repeated traffic to one link but is not a global DDoS or billing cap. Invalid routes do not access KV; missing-key requests have a short bounded negative cache and simultaneous reads coalesce, without per-click KV writes. New links may remain absent in this cache for up to three seconds; authenticated self-tests bypass it.

For ordinary successful GET clicks only, a keyed digest of canonical link, available IP and bounded User-Agent supports a bounded in-memory 30-minute first-seen window. It stores neither raw IP nor raw User-Agent, emits no visitor identifier, sets no cookie, and is not a unique-person metric. Repeated clicks still redirect normally. Cross-location/instance traffic, eviction, secret changes and restarts can count again; missing signals or full capacity produce unmeasured events, not fabricated new visitors. Work runs under `ctx.waitUntil` so successful redirects do not wait for statistics. Weighted SQL sums double2 and double3 and validates nonnegative safe integer values and `first+repeat<=total`; preview/prefetch indicators must be zero. Old data has no dedup coverage. The UI retains raw request totals alongside estimated first/repeated counts and coverage, showing unmeasured nonempty data as unavailable rather than zero people. No historical unique counts are reconstructed.
